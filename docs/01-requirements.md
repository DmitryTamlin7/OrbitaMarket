# 1. О приложении

## 1.1. Назначение

OrbitaMarket — распределённая платформа для заказа и оплаты продуктов дистанционного зондирования Земли (ДЗЗ).  
Система автоматизирует полный цикл: создание заказа → асинхронная оплата → изменение статуса заказа.

Платформа решает задачу оперативной покупки спутниковых данных без ручного согласования и ручного биллинга.

## 1.2. Пользователи и роли

| Роль              | Кто это                          | Основные действия                                      |
|-------------------|----------------------------------|--------------------------------------------------------|
| Пользователь      | Сотрудник аналитической компании, оператор ДЗЗ, внутренний пользователь | Создаёт заказы, пополняет баланс, смотрит историю и статус заказов, получает доступ к данным |
| Система (сервисы) | Внутренние микросервисы          | Обрабатывают события оплаты, обновляют статусы, обеспечивают идемпотентность |

На текущий момент явной роли «Администратор» нет — все действия выполняются от имени покупателя через заголовок `X-User-Id`.

## 1.3. Что уже умеет система (на момент начала работы)

- Создание заказа на продукты типов **ARCHIVE**, **TASKING**, **MONITORING** с полиморфной полезной нагрузкой (AOI, временные окна, cadence).
- Автоматическое создание финансового кошелька пользователя (geocredits) при первом обращении.
- Пополнение баланса и списание средств.
- Асинхронная обработка оплаты через Apache Kafka (события `payment-requests`, `payment-completed`, `payment-failed`).
- Защита от повторного списания (идемпотентность по `orderId`).
- Просмотр списка заказов пользователя и детального статуса конкретного заказа.
- Единая точка входа через API Gateway.
- Кэширование баланса (Cache-Aside).

## 1.4. Основные термины

| Термин              | Значение                                                                 |
|---------------------|--------------------------------------------------------------------------|
| **ARCHIVE**         | Заказ на уже существующие архивные спутниковые снимки                    |
| **TASKING**         | Заказ на будущую съёмку (полетное задание)                               |
| **MONITORING**      | Подписка на периодический мониторинг территории                          |
| **AOI**             | Area of Interest — полигон области интереса                              |
| **geocredits**      | Внутренняя валюта системы (единицы баланса кошелька)                     |
| **orderId**         | Уникальный идентификатор заказа, используется как ключ идемпотентности   |
| **PENDING_PAYMENT** | Начальный статус заказа после создания                                   |
| **PAID / FAILED**   | Финальные статусы после обработки платежа                                |

## 2. Требования к функционалу

### 2.1. Функциональные требования

| №     | Требование                                                                 | Приоритет              | Состояние          | Признак выполнения                                                                 |
|-------|-----------------------------------------------------------------------------|------------------------|--------------------|------------------------------------------------------------------------------------|
| FR-1  | Пользователь может создать заказ на продукт типа ARCHIVE, TASKING или MONITORING | Обязательно            | Уже есть           | Система возвращает `201 Created` и `orderId`, заказ сохраняется со статусом `PENDING_PAYMENT` |
| FR-2  | Пользователь может просмотреть список своих заказов                        | Обязательно            | Уже есть           | Система возвращает массив заказов пользователя с актуальными статусами             |
| FR-3  | Пользователь может просмотреть детальную информацию по конкретному заказу  | Обязательно            | Уже есть           | Система возвращает полные данные заказа по его UUID                                 |
| FR-4  | Пользователь может получить или автоматически создать финансовый кошелёк   | Обязательно            | Уже есть           | При первом обращении создаётся кошелёк с балансом 0, при повторном — возвращается существующий |
| FR-5  | Пользователь может пополнить баланс своего кошелька                        | Обязательно            | Уже есть           | Баланс увеличивается на указанную сумму, кэш сбрасывается                          |
| FR-6  | Пользователь может оплатить заказ (средства списываются с кошелька)        | Обязательно            | Уже есть           | При достаточном балансе заказ переходит в статус `PAID`, при недостаточном — в `FAILED` |
| FR-7  | Пользователь может получить доступ к архивным данным после успешной оплаты | Желательно             | Нужно сделать      | После статуса `PAID` пользователь получает ссылку (signed URL) на скачивание данных |
| FR-8  | Пользователь может отменить заказ до момента оплаты                        | Потом                  | Нужно сделать      | Заказ переходит в статус `CANCELLED`, средства не списываются                      |

### 2.2. Ограничения (Non-Functional Requirements)

| №     | Ограничение                                                                 | Приоритет     | Состояние     | Как проверить                                      |
|-------|-----------------------------------------------------------------------------|---------------|---------------|----------------------------------------------------|
| NFR-1 | Система должна работать через единую точку входа (API Gateway)             | Обязательно   | Уже есть      | Все запросы идут только через порт 8080            |
| NFR-2 | Время ответа на чтение баланса и списка заказов не превышает 500 мс при наличии данных в кэше | Обязательно | Уже есть (in-memory) / нужно доработать (Redis) | Нагрузочный тест k6 + проверка latency             |
| NFR-3 | Система должна защищать от повторного списания средств (идемпотентность)   | Обязательно   | Уже есть      | Повторная доставка одного и того же `orderId` не приводит к двойному списанию |
| NFR-4 | Чувствительные данные (пароли БД, ключи) не хранятся в коде и репозитории  | Обязательно   | Уже есть      | Gitleaks / Semgrep не находят секретов             |
| NFR-5 | Приложение разворачивается и запускается через Docker Compose              | Обязательно   | Уже есть      | `docker compose up --build -d` успешно поднимает все сервисы |
